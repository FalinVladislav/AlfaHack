# Синтетическая финансовая история

`finance-schema.sql` расширяет профиль компаний и создаёт таблицы по структуре макета. `SyntheticFinanceData` запускается после основного `SeedData`, заполняет только отсутствующие наборы и не заменяет пользовательские заявки или выданные кредиты. Поддерживаются прежние H2 и PostgreSQL.

| Таблица | Основные поля | Назначение |
| --- | --- | --- |
| `companies` | `company_id`, `okved`, `business_age`, `industry`, `employees`, `annual_revenue` | Профиль предпринимателя; прежние `id`, `name`, `balance` сохранены. Возраст бизнеса — в месяцах. |
| `transactions` | `company_id`, `date`, `amount`, `type`, `category`, `counterparty_id` | История поступлений и расходов. Сумма положительная, направление задаёт `INCOME`/`EXPENSE`. |
| `balances` | `company_id`, `date`, `balance` | Исторические остатки на конец дня. |
| `existing_loans` | `company_id`, `remaining_debt`, `monthly_payment`, `rate`, `next_payment_date`, `end_date` | Исходная долговая нагрузка, ближайшие списания и срок окончания. |
| `loan_products` | `product_id`, `type`, `rate`, `min_amount`, `max_amount`, `min_term`, `max_term`, `requirements` | Копия действующего демонстрационного каталога. |
| `loan_requests` | `company_id`, `goal`, `requested_amount`, `expected_revenue_growth`, `expected_expense_growth`, `project_cost` | Примеры потребностей предпринимателя; показатели роста — гипотезы, а не прогноз или обещание. |

Для каждой из двух компаний создаются 30 операций за 6 завершённых месяцев, ежедневные остатки за последние 6 месяцев, 2 действующих обязательства и 2 примера потребностей. Каталог содержит 5 продуктов. Все контрагенты и суммы вымышлены.

Остатки восстанавливаются назад от текущего баланса компании по тем же операциям. Месячные суммы API агрегируются из `transactions`, а не задаются отдельно во frontend. `balances` — исторические снимки; актуальный доступный баланс берётся из `companies.balance`. Выдача через кабинет продолжает записываться в прежние `loans` и `ledger_events`.

Фича `finance` соблюдает принятую структуру `application` → `port` ← `adapter/out/persistence/jdbc`. `GET /api/v1/finance/overview` возвращает финансовую историю текущей компании. `GET /api/v1/finance/loans` объединяет `existing_loans` с выданными через кабинет `loans`, добавляет дату окончания для новых выдач и сортирует по дате ближайшего списания. Оба метода доступны только клиенту и проверяют принадлежность компании через сессию.

Долговая нагрузка на главной — сумма текущих платежей по обязательствам, делённая на доход последнего завершённого месяца. При подаче заявки `ScoringEngine` использует сохранённые показатели компании, операции и обязательства для рекомендации. Окончательное решение принимает закреплённый сотрудник; название подготовленного профиля на него не влияет.
