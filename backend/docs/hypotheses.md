# Формирование гипотез

Главная использует `GET /api/v1/hypotheses` (совместимый адрес — `/insights`). Запрос собирает снимок доступных данных, но не ждёт модель. Обработка выполняется фоновым worker бэкенда. Отдельный сервис `inference` отвечает только за объяснение.

## Данные и основания

Снимок содержит профиль компании, месячные поступления и расходы, действующие кредиты, до трёх заявленных целей, каталог продуктов и расчёты известных событий на 30 дней и 6 месяцев. SHA-256 вычисляется по каноническому JSON, включая дату и версию алгоритма. Одинаковые данные одной компании используют одно задание; новые данные создают новое. Клиент не передаёт company_id.

В первой версии реализованы два основания:

- Отрицательный остаток в плане на 30 дней → гипотеза о пересмотре графика платежей или краткосрочном финансировании. Размер недостатка вычисляет бэкенд. Статус `CALCULATED` относится к плану известных событий, а не к прогнозу будущей выручки.
- Заявленная цель из `loan_requests` → гипотеза о проверке спроса и экономики до вложения. Статус `NEEDS_DATA`. Запрошенная сумма и проценты ожидаемого роста не являются доказательством эффекта.

Если оснований нет или модель не предложила гипотезу, результат `EMPTY`. Система не добавляет обязательное число карточек и не обещает рост доходов. `EXPERIMENT_ONLY` зарезервирован в контракте для будущих гипотез, эффект которых проверяется экспериментом; текущие правила этот статус не выставляют.

Исходные финансовые данные синтетические. В этой итерации их генератор не меняется. Новые сценарии можно задавать согласованными изменениями `transactions`, остатков, плановых `ledger_events` и целей `loan_requests`. Для проверки случая без оснований используйте компанию без целей и отрицательных плановых остатков.

## Фоновая обработка

`insight_jobs` хранит снимок и состояние: `QUEUED → RUNNING → READY | EMPTY | PARTIAL | FAILED`. Worker проверяет очередь каждые 2 секунды и последовательно обрабатывает до четырёх кандидатов одного снимка. Долгий вызов модели не удерживает транзакцию или блокировку БД.

Кандидат передаётся через `/v1/assist` с `scenario=growth_hypotheses`. Модель возвращает объяснение, первый эксперимент, критерий результата и вопросы. Она не выбирает сумму, срок и кредитный продукт: эти поля остаются серверными.

Каждая готовая карточка сохраняется отдельно в `business_hypotheses`, поэтому появляется до завершения всей подборки. При недоступности модели сохраняется разбор по правилам с `explanation_source=RULES`; задание получает `PARTIAL`. Без настроенного MODEL_API_URL работает режим правил и статус `READY`. Никакие ответы провайдера с секретами не сохраняются в сообщениях ошибок.

Повтор `POST /hypotheses/refresh` переочередит только `FAILED` или `PARTIAL` для тех же данных. UUID карточки зависит от задания и основания: повторное объяснение обновляет карточку без нового уведомления и без сброса прочтения. При отсутствии новых данных `READY` и `EMPTY` не вызывают модель повторно.

Задание захватывается условным UPDATE и получает lease_token. Если обработчик пропал, `RUNNING` без обновления более 5 минут доступен для повторного захвата. Старый обработчик с потерянным lease не может сохранять карточки или завершать задание. Не увеличивайте таймаут одного вызова модели до пяти минут без увеличения срока аренды. Перезапуск бэкенда сохраняет очередь и результаты.

Данные обнаруживаются при запросах `/hypotheses`: открытие кабинета, фоновый опрос, ручное обновление. Вне открытого кабинета новые снимки автоматически не создаются; уже созданные задания продолжают выполняться. Для непрерывной обработки всех компаний позже можно добавить плановый сбор снимков или события изменения данных.

## Финансирование

После объяснения показываются предварительные варианты по цели, запрошенной сумме и демонстрационному сроку: 36 месяцев для развития, 12 для оборотных средств, 30 дней для разрыва. Расчёты выполняет существующий `ProductCatalog`. Варианты упорядочены по общей сумме возврата при одинаковом сроке. Это сравнение условий, а не оценка оптимального срока или одобрение.

Для краткосрочного варианта дополнительно проверяется остаток на дату возврата по известным событиям шестимесячного плана, с зачислением и погашением транша. `PLAN_SHORTFALL` запрещает переход к оформлению этого варианта в UI; `PLAN_ONLY` не подтверждает платёжеспособность. Проверка всего графика и обычное кредитное решение выполняются существующим процессом оформления.

Страница гипотезы проверяет актуальность снимка. Для устаревшей версии кнопки финансирования отключены; главная получает текущую подборку. Переход по подходящему варианту создаёт обычный черновик с суммой, целью, сроком, датой и product_id. Пользователь подтверждает дальнейшие действия сам.

## Интерфейс и уведомления

На главной остаются заголовок и краткий статус; вся карточка открывает объяснение, без отдельной надписи «Подробнее». Страница `#hypothesis/{id}` содержит объяснение, раскрываемые факты, допущения, вопросы и кредитные варианты. Главная не ждёт гипотез для показа финансовых карточек. Место под гипотезу зарезервировано и при пустой подборке, поэтому финансовые блоки не растягиваются и не сдвигаются при появлении карточки.

Frontend опрашивает гипотезы и уведомления каждые 3 секунды при `QUEUED/RUNNING` и каждые 15 секунд после завершения. Ошибка сети не удаляет ранее полученные данные; следующий опрос повторяет запрос. Смена пользователя отменяет старые запросы.

`GET /notifications` возвращает последние 50 карточек своей компании как уведомления. Колокольчик отмечает непрочитанные; открытие карточки отмечает соответствующее уведомление через `POST /notifications/{id}/read`. Прочтение хранится в `insight_reads` отдельно для каждой учётной записи. Повторная отметка безопасна. Изменяющие методы требуют CSRF, чужие карточки возвращают 404.

Полный контракт находится в [openapi.yaml](openapi.yaml) и Swagger. Worker отключается переменной `INSIGHTS_WORKER_ENABLED=false`; это удобно для тестов с ручным `processNext()`.

## Проверки

`HypothesesIntegrationTest` проверяет очередь без синхронного вызова модели, дедупликацию снимков, появление карточки и уведомления до завершения задания, отказ модели, повтор без дубликатов, пустой результат, изменение данных, режим правил, восстановление зависшего задания, изоляцию компаний, сессии и CSRF.

Тесты используют управляемую модель без внешних запросов. Контракт HTTP-провайдера отдельно проверяется тестами `inference`.
